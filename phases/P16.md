# P16 — Multi-region core (regions registry + `?region=`)
**Depends on:** P01–P15 · **Refs:** D-22, planning §6 (per-region metric CRS), §8 (`?region=`)

## Goal
The app can hold several pilots side by side. Salt Lake Sector V keeps working unchanged (default region); new regions plug in by config + their own data folder.

## Steps
1. `config/regions.yaml`: id, name, city, state/country, centre, curated study boundary (rectangle unless an official polygon exists), timezone, `metric_crs` (UTM zone), AQ index (`naqi` | `daqi` | `nsw_aqc`), design storm mm/h, OSM source, notes. `sector_v` = existing data in `data/processed/` (no move); others in `data/processed/regions/<id>/`.
2. Backend: `core/regions.py` (registry, `region_dir(id)`, `metric_crs(id)`), FastAPI dependency `region: str = Query("sector_v")` → 404 unknown. Every cached singleton (layer store, graph, flood context, access graph, landcover, climate, surrogate, health) keyed by region; lazy-load non-default regions. Engines take the metric CRS from the data (no hard-coded 32645). Weather/air/climate use the region centre + timezone. `GET /api/regions` (id, name, country, status `ready|no-data`, bbox, centre).
3. Pipelines: `HYPERBOREA_REGION=<id>` env selects boundary + output folder; same scripts for every region. `python -m pipelines.make_region_boundary` writes the curated boundary.
4. Frontend: region switcher in the header (only `ready` regions); all API calls carry `?region=`; deep link `?region=`; camera flies to the new region; layers/scenarios/development reset on switch. Snapshots per region: `snapshots/<region>/...` for non-default regions (default keeps current names).
5. Tests: registry valid (CRS matches the centre's UTM zone), unknown region 404, default region == old behaviour (existing tests green), per-region caches isolated.

## Acceptance
Switcher lists Sector V (others appear as data arrives in P17–P19); every existing test passes unchanged; `?region=nope` → 404.
